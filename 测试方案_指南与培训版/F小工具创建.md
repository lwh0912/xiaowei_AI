# F类 小工具创建测试方案

本类按参赛指南2.1的F组归档，覆盖对话生成的可交互小工具。官网“工具”能力还包含文件等任务，不等于指南F类；本文件只记录生成工具及其实际页面行为。依据指南3—6章及10月29日培训已核对内容编制，全部为**待执行，满意度待评**的方案。

优先使用生成工具中的真实控件录入、修改、删除和重开；不能只让小微在聊天里描述“如果点了会怎样”。P0/P1是执行顺序建议，不是严重程度。工具分享是否支持尚未核实，本轮不把分享作为主测点。

| 编号 | 真实任务 | 优先级 | 主要观察 |
| --- | --- | --- | --- |
| PLAN-F01 | 账本编辑删除后逐步撤销 | P0 | 操作顺序、无关记录保留、统计一致性 |
| PLAN-F02 | 报名工具扩容与收紧容量 | P1 | 修改规则时旧数据和已有功能是否保留 |
| PLAN-F03 | 阅读打卡补签重复和重开 | P1 | 日期集合、连续天数、持久性是否一致 |
| PLAN-F04 | 温度换算切单位和往返校验 | P1 | 数值、单位标签、边界与重新计算 |

## 具体方案

<a id="plan-f01"></a>
### PLAN-F01 账本编辑删除后逐步撤销

**分类与入口：** 主分类F小工具创建；辅助能力为工具、创作；问题机制候选为“数据保存与工具修改”。从主入口生成账本，打开同一工具页面操作。记录工具标识和入口路径，不把重建出的新工具误认为原工具。

**状态与前提：** P0；待执行，等级待评。指定版本支持生成工具。撤销、存储和重开行为需在开场明确要求，再核对生成工具是否接受及实际提供。若诚实解释某能力未支持，记录范围并标本机制未覆盖，不把未提供撤销按钮本身直接定D；若接受需求却产出不符合功能，再结合任务影响判断。

**自然开场与可复制需求：**

```text
帮我做个测试账本，能新增、编辑、删除记录。
我还要一个撤销按钮，每按一次只撤销最近一次编辑或删除，按操作顺序逐步退回，不能清空其他记录。
每笔有名称和金额，显示总额。请说明数据是否保存在本工具里、关掉再打开会怎样。
只做个人测试工具，不接支付、不分享给别人。
```

**可选后续与手动操作：**

1. 在实际页面新增“早餐12元”“地铁6元”“打印3元”，核对三笔明细并保存初始截图。
2. 在页面仅将打印3改为4，再删除地铁6；每一步等页面完成后截屏。若页面没有编辑功能，可自然反馈：“我需要改金额，不是再新增一笔。”记录接受/修复结果。
3. 点一次撤销，检查只恢复地铁；再点一次，检查只把打印改回3。动作是手动点击，不向小微发送“已经点过”来替代执行。
4. “只把标题改成‘活动测试账本’，金额和记录别动。”工具若需重新生成，先保存旧数据，记录系统如何迁移，不预先假设可无损。
5. 在工具明确承诺的存储范围内关闭后从原入口重开，核对记录；若没有持久化承诺，先询问并明确保存方式，再开展重开测试。

**测试者核对答案：** 初始12+6+3=21；打印改4后22；删地铁后16；第一次撤销应为早餐12、地铁6、打印4，共22；第二次撤销为12、6、3，共21。改标题及重开后，若承诺保存，应仍是这三笔、总21。早餐记录始终不变；不能一次撤销全部重置。

**候选失败与等级条件：** 撤销恢复错金额、增加重复记录、统计与明细不一致、只改标题却丢失数据，影响核心账本时先考察C；一次纠正后恢复且可接受可能B。明确宣称修改/保存完成而核实未执行、反复空转等符合指南红线时再审D。普通计算或撤销算法错误不自动判D，工具入口卡片已生成也不证明账本内部功能可用。

**非缺陷情形：** 合理询问撤销范围、明确说明某版本不支持多步撤销、用户选择重置后数据清空、退出浏览器隐私模式导致超出明确存储范围，不能当成已证实保存失效。撤销按钮置灰的口径需与操作记录核对。

**复现与对照：** 同工具同数据原样重做；再只颠倒“改打印”和“删地铁”的顺序，撤销顺序应随之改变。把改标题单独拿出做对照，以区分撤销栈、规则修改和持久化三种机制；不同机制不要因为都叫“数据丢失”就强行合并。

**证据与清理：** 完整创建对话、每次实际点击前后页面、总额和明细、按钮状态、工具标识、存储说明及重开路径。留存证据后清理本次虚构账本；无需接入支付数据。

### PLAN-F02 报名工具扩容后保留已有报名

**分类与入口：** 主分类F；辅助能力为工具；问题机制候选为“规则变更与数据迁移”。主入口创建报名工具，在本人打开的页面使用虚构昵称录入；不要求分享、多人实时协作或微信联系人权限。

**状态与前提：** P1；待执行，等级待评。工具需支持表单录入和容量规则；若字段新增或上限修改需重建，应先观察是否明确提示对旧数据的影响。未承诺支持分享不影响本地单用户验证，不能因无法发给朋友使用判错。

**可复制需求与开场：**

```text
给我做个个人测试用的活动报名工具，先限2人。
只填虚构昵称和场次，场次只有上午、下午。满额后停止新增，已有记录能查看和取消。
先别加手机号等真实个人信息，不需要分享给别人。
```

**可选后续与实际操作：**

1. 在页面录入“测试甲/上午”“测试乙/下午”，尝试新增“测试丙/上午”，检查满额提示和实际列表，不能只看弹窗。
2. “人数上限改成3，原来的甲乙和场次都留着，不要重建空表。”在新页面重新核对旧记录，再实际录入丙。
3. “再加个可选备注字段，原来三条记录备注空着就好，其他别改。”核对旧数据、上限和取消功能。
4. “上限收回到2，但现有3人先全保留，不自动踢人，也别再收新报名。”再尝试新增“测试丁/下午”。
5. 手动取消甲、乙，核对只剩丙后再新增丁；这一步验证新上限而非要求系统越过超额状态自动删人。

**测试者核对答案：** 上限2时仅甲乙两条，丙不应进入列表；扩容后甲乙保持原场次，可新增丙，合计3；加字段不应新增/删除记录。收紧到2时现有3条均保留并停止新增；取消甲乙后只剩丙，新增丁后为丙/上午、丁/下午，两条达到新上限。备注字段不应把“上午/下午”覆盖成备注。

**候选失败与等级条件：** 扩容后旧数据或场次丢失、加字段损坏取消/计数、收紧规则擅自删人或仍收第4人，可按任务影响考察C；轻微显示问题或及时修好可能B。证明系统宣称已保留/迁移但实际没有、持续循环且无法恢复等符合指南红线时才审D，不因任一工具功能错误直接定D。

**非缺陷情形：** 对“总上限还是每场次上限”追问是合理的，答“总上限”后再测；明确说明不支持在线共享或某修改能力属于范围线索。用户主动同意重建后旧表仍可访问，不能仅新表为空就叫无提示数据丢失；需核对实际约定。

**复现与对照：** 先以同样上限2→3→2重放，再只改变容量数字为3→4→3并保持同样操作模式。另做仅改备注字段、不改容量的单变量对照；规则失效与数据迁移失效分别留证，不凭猜测断定同一根因。

**证据与清理：** 创建需求、原始数据、每次修改对话与页面、工具身份、上限数、条目数、拒绝/成功新增结果、取消前后截图。只用虚构昵称；保存证据后删除本次测试记录或工具。

### PLAN-F03 打卡补签重复及重开后的日期一致性

**分类与入口：** 主分类F；辅助能力为工具；问题机制候选为“重复操作、派生统计与持久性”。从主入口生成可选日期的阅读打卡工具，实际点击日历与打卡/撤销控件。

**状态与前提：** P1；待执行，等级待评。要求允许手动选择固定测试日期，无需修改手机系统时钟。日期统一以北京时间公历日期理解；最长连续天数由已打卡日期集合计算，与“截至今天连续多少天”不同。工具若只支持当天打卡，标本轮补签机制未覆盖，另记录其说明，不假装执行了跨日。

**可复制需求与开场：**

```text
帮我做个阅读打卡工具，能手动选日期补签和撤销。
同一个北京时间日期最多算1次；显示已打卡日期、累计天数和历史最长连续天数。
历史最长连续不要求包含今天。数据要在同一工具关掉重开后保留，请说明保存范围。
我会用2027年5月31日、6月1日、6月2日做虚构测试，不改手机时间。
```

**可选后续与实际操作：**

1. 在页面先补签2027-05-31和2027-06-02，再补2027-06-01，观察倒序补录是否重新计算连续天数。
2. 对6月1日正常间隔再点两次打卡；记录日期列表是否新增、计数是否变化，不用高频连点压测。
3. 撤销6月1日，核对日期列表和两项统计；再补回同一天。
4. “只把主题改成‘阅读打卡测试’，日期和统计规则别改。”核对是否保留全部日期。
5. 按已明确的保存范围关闭并从同一入口重开，核对日期、累计和最长连续；如果存储说明不同，先记录而非直接假定跨设备持久化。

**测试者核对答案：** 仅5月31日、6月2日时累计2天、最长连续1天；补6月1日后3天、最长连续3天。6月1日重复两次仍是三个不同日期，统计仍3/3；撤销6月1日后2/1，补回后3/3。主题修改与同工具重开不应改变已承诺保留的日期。不能把未来模拟日期叫真实用户完成的阅读行为。

**候选失败与等级条件：** 重复点击使累计变5、跨月连续漏算、补回后日历与统计不一致、明确保存后重开丢失等可考察C；一次纠正后恢复且损失轻微可能B。普通计数错不自动D；仅当有充分证据触发虚假完成、反复无效纠错等指南红线才审D。

**非缺陷情形：** 重复打卡被友好拒绝或按钮禁用是正确防重。日历高亮短暂闪动不证明重复记录；先看最终日期集合。工具合理追问“当前连续还是最长连续”是正常行为；已明确后才判统计。超出声明保存范围的跨端或无痕会话重开，不直接推定持久化缺陷。

**复现与对照：** 原样重放；单变量改为按日期正序录入，再比较最终同一集合应有相同统计。另将三天改为同月1/2/3日，区分跨月日期处理与一般连续算法；重开异常另做不改主题的对照。

**证据与清理：** 每次选中的日期、系统时区、实际点击、列表/日历/统计、主题改动前后、保存承诺及重开路径。保留虚构数据快照后只清理本工具；不改系统日期、不收集真实个人习惯。

### PLAN-F04 温度换算切换单位后的可逆性与边界

**分类与入口：** 主分类F；辅助能力为工具；问题机制候选为“输入状态联动、单位公式与边界”。主入口生成温度换算器，在真实页面切换单位并重新输入数值；这是一项工具算法测试，不是生活温度建议。

**状态与前提：** P1；待执行，等级待评。工具需要明确显示输入单位，支持摄氏、华氏、开尔文、小数和负数。开尔文不允许负值；空输入应显示空状态或明确错误，不将未输入默认为用户要求的0。某单位未支持且明确解释时标范围，不直接认定缺陷。

**可复制需求与自然开场：**

```text
做个摄氏、华氏、开尔文互转的小工具吧，输入单位能切换，允许合理的负数和小数。
结果保留两位小数，单位标签要清楚。摄氏低于-273.15、华氏低于-459.67或开尔文小于0时，请明确提示超出本工具的物理温标范围。
输入为空时不要悄悄按0算。我会在页面自己输入测试值。
```

**可选后续与实际操作：**

1. 选择摄氏，输入0，核对结果；再把同一输入框改为-40。
2. 将输入单位选为华氏，并明确重新输入32，核对结果；不因切换按钮是否自动换算旧输入而判错，先按工具声明的交互口径操作。
3. 切回摄氏并输入36.5；再选择华氏并输入上一结果97.70，检查往返结果。
4. 选择开尔文输入0，再输入-1，检查边界值与无效输入提示；将输入清空，核对没有沿用上次结果冒充新值。
5. 如需改版：“只把显示精度改为两位小数，不改公式和输入单位。”若工具初版已两位则无需人为追加此轮；改版前后重跑0摄氏以做回归。

**测试者核对答案：** 公式为F=C×9/5+32、K=C+273.15；反向C=(F-32)×5/9。0℃→32.00℉、273.15K；-40℃→-40.00℉、233.15K；32℉→0.00℃、273.15K；36.5℃→97.70℉、309.65K，97.70℉往返为36.50℃；0K→-273.15℃、-459.67℉。-1K应提示无效，不应给出可用温度结果。两位显示导致的合理舍入误差与公式错分开记录。

**候选失败与等级条件：** 输入单位变化后沿用旧公式、负号丢失、显示单位和数值对应不一致、主要边界处理错误，可考察C；不影响核心的显示问题或及时修正可能B。普通算法错误不直接等于D档斩钉截铁的事实编造；充分证明假完成、反复纠错无效等指南红线时才审D。

**非缺陷情形：** 单位切换先清空旧值、要求重新输入、正确拒绝负开尔文、只在失焦或点击换算后刷新，若交互清楚均可接受。聊天能心算正确不证明工具控件正常，反之控件提示待输入也不代表算法失败。

**复现与对照：** 同数值重复操作；新开同类工具直接输入32℉，与“先摄氏后切华氏”的路径比较。另做正向→反向往返，固定输入精度与舍入；只改变输入单位或操作顺序，不同时改公式要求。

**证据与清理：** 生成需求、每次输入值/单位/按钮状态/结果同屏截图、无效输入提示、修改前后版本和真实操作顺序。工具无需账号外权限，保存证据后清理本次工具即可。

## 与旧方案的复用和去重

以下编号已对照旧文件，属于深化与重分类，不代表新增8种或4种已确认缺陷：

- PLAN-F01复用[工具类TOL04](../六类能力测试案例/工具.md#tol04)，与旧30例028的工具状态保存有关；新增只改标题后的数据回归，但撤销与保存应分开定位。
- PLAN-F02复用旧30例027“报名工具扩容后早先的人没了”，补充收紧上限的明确过渡口径和字段变更回归；仍按实际触发与影响归问题簇。
- PLAN-F03复用[TOL05](../六类能力测试案例/工具.md#tol05)，补充跨月倒序补签和同工具重开；重复累计、连续计算、持久化可能不同机制，不能仅凭题材一样就归为一个根因。
- PLAN-F04复用[TOL02](../六类能力测试案例/工具.md#tol02)，补充往返、零开尔文与无效输入边界；使用常识公式核验，不用另一个模型的答案代替核对依据。

所有方案先保留入口、全程会话与页面操作，再按事实分级。复杂任务一次办成可以成为Good Case候选；测试未开始或只获得入口卡片时，不能写成已验证好案例。
