# 按老师模板执行与记录

本方案从2026-10-29起使用[老师模板](../老师模板/README.md)，不再另建一份简化的正式案例表。

1. 待测任务先在[执行台账](./执行台账.md)记录计划ID、准备状态和实际环境。
2. 有实际反馈后，复制[Bad Case记录模板](../老师模板/BadCase记录模板.md)或[Good Case记录模板](../老师模板/GoodCase记录模板.md)，按原字段顺序填写；未判断类型时先保留原始会话，不抢填等级。
3. 总结真实探索时使用[测试报告模板](../老师模板/测试报告模板.md)。报告中的规律要有真实已提交案例支持，不由待测任务生成“发现”。

## 可附的本地过程资料

这些是复盘辅助，正式表单字段仍须完整保留：

- 执行编号、关联PLAN编号、原BC/GC编号及问题簇：
- 实际时间及时区、设备、系统、微信/小微版本、网络：
- 真实点击入口、可见上下文、权限、记忆和同步开关：
- 输入材料/版本、最初条件、逐轮改动、最终有效条件：
- 真实文件/工具/提醒状态及核对依据：
- 预先定义的有效尝试和分母；外部中断与产品无响应分别记录：
- 同条件复现与单变量对照，实际是否覆盖特定机制：
- Q1—Q7或其他本地机制标签、改进建议和未解决的证据缺口：
- 清理前证据及本轮提醒、草稿或工具清理结果：

图数、消息数和小微自述次数不等于独立测试次数。产品卡住不能因没有走到后续步骤就从任务结果中剔除。Bad统计问题出现次数，Good统计一次办成次数，二者不混算。

## 提交前核对

- [ ] 原表单必填字段齐全；真实入口、轮数、平台及次数都有依据
- [ ] 完整截图覆盖第一轮至末轮；附件与真实产出可核对且已脱敏
- [ ] 类型、场景、满意度、问题/亮点类型分开，没有将Q标签替代正式选项
- [ ] 一例一Issue，Bad/Good标题保持默认，具体结论在总结字段
- [ ] 提交确认条款由参赛者实际阅读并决定勾选
- [ ] 真正提交后才记[提交台账](../老师模板/提交台账.md)及回执；没有自动向CNB提交
