# 小微AI 六类能力测试案例

这套案例按官网的社交、内容、工具、生活、创作、设置六类能力组织，共60个待实测探索路径。目标是提高高价值问题的发现机会，兼顾证据完整、可复现和正确分级。它们不是60个已发现问题，也不代表60种独立缺陷。与原30例有交叉的地方已注明关联，原文件保持保留。

## 从这里开始

先选自己有实际需求、指定版本已开放的能力。下面每类选2例作为第一批，完成后按失败机制扩展，而不是把60例机械跑完。P0表示输入和判据较明确、建议先做；P1表示需要特定能力或素材；P2表示准备依赖更多或对照较复杂。优先级不是严重程度，也不是命中率预测。

## 怎样更容易发现有效问题

1. 一次围绕一件实际任务深入使用。先得到初版，再自然修改人数、对象、金额、时间或格式。重点看改动是否只影响应改的内容，以及最终产物是否沿用旧值。
2. 尽量保留完整任务链。先提取或检索，再整理、计算、生成工具或文件；逐个核对中间结果，定位是识别错误、计算错误还是传递错误。
3. 发现异常后先留证，再纠错。第五轮的复核通常用于定位错误，不要把明确答案提前塞给模型。若小微合理追问，先补齐缺失条件；若纠错后快速办成且整体可接受，可能应判B。
4. 先在相同条件复现，再只改一个变量做对照。可换入口、数据顺序、近似名称、轮次或模态；记清问题出现次数和有效尝试次数。建议至少再试两次，但这只是个人执行建议，不是官方硬性门槛。
5. 找到同机制的多个表现时，归为一个问题候选，选证据最完整的一条作为主例。不同数据或入口的复现记录作补充，不按数量重复堆提交。

固定日期、金额、路线和人物用于可控的合成测试，不代表真实预约、价格或身份。若任务需要真实日期，将绝对时间改为测试日之后，并在每轮保持同一基准。按步骤实际点击工具时，应拍下操作前后的界面；不能只让小微口头推演点击结果。

## 分级时保留这些边界

- A：一次办成、约束完整、实际产出可用。复杂或新颖的A例可另走Good Case模板。
- B：核心任务办成，有可接受的小瑕疵或及时纠错。
- C：主要需求未满足、反复折腾或结果有实质缺陷。普通算错、改图漂移、跨轮约束丢失通常先检查这一档。
- D：需充分证据命中指南红线，包括虚假完成、确定性编造、复读或纠错无效、任务失败无补救、安全泄露或贬损、该拒未拒。不能因为一句“已完成”就直接判D，先确认它指的是生成草稿还是真实动作，并排除仍在生成、确认未完成、入口未开放、同步延迟和附件折叠。
- X：台账用于标记无效反馈，不是满意度第五档。正确拒答、友好性格、合理耗时、解释到位的不支持等，不应作为Bad Case提交；明确不支持后合理降级不等于任务失败无补救。

“修改后仍复述同一句话”不必然达到D档循环红线。保留完整纠错链，说明为什么核心问题持续未解决。凭空出现一个标记或人名也不能直接证明真实隐私读取，应排除当前上下文、记忆、输入材料和随机补全的影响。

## 每个有效发现保留什么

记录客户端版本、设备、入口点击路径、权限和记忆条件、网络、时间；保留最初材料、每轮用户消息与回复、实际点击、完整截图和真实文件/工具/提醒列表。实际结果与预期分开写，说明错误首次出现在哪一轮、影响是什么，以及复现情况。

按现有[案例记录模板](../案例记录模板.md)建立一份记录，归类时填写观察到的机制，不臆测内部技术原因。截图与附件脱敏；Issue标题可能公开，实质内容放在私密正文。正式提交仍以赛事发布的模板与规则为准。

涉及消息、朋友圈、通话、付款、订单和账户设置的案例，默认使用自控测试对象，只做到草稿、方案或预览。真正需要创建的测试提醒、工具和笔记在案例前提中另列，记录初始状态并在结束后清理。缺少能力或必要授权时标“不适用”，不把功能未开放当成问题。
