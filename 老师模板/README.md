# 老师提供的小微案例记录模板

接收日期：2026-10-29。来源：用户指定的桌面 `template` 文件夹，内含三份YAML提交表单，没有独立的已执行案例文件。源文件未注明版本号或发布日期；本项目按用户要求采用此版记录，正式提交前仍与CNB实际表单核对。

**今后记录案例，直接复制下方对应模板，保留字段顺序、名称、必填性和单选项。** 未知信息写待补，不为了填满表单虚构入口、轮数、测试次数或平台；填写草稿不会自动创建Issue、提交材料或同意确认条款。

| 类型 | 可复制填写稿 | 原始表单 | 用途 |
| --- | --- | --- | --- |
| Bad Case | [问题案例记录模板](./BadCase记录模板.md) | [xwbadcase.yml](./原始模板/xwbadcase.yml) | 一条实际问题；等级B/C/D |
| Good Case | [优质案例记录模板](./GoodCase记录模板.md) | [xwgoodcase.yml](./原始模板/xwgoodcase.yml) | 一条有复杂度/新颖性的正向案例；本版允许A/B |

[字段对照](./字段对照.md)逐项列出ID和必填性；[源文件校验](./原始模板校验.json)保存三份原文件的SHA256，防止混用版本。[提交台账](./提交台账.md)记录真实Issue与提交顺序，不预设已有提交。

## 以后怎样记录

1. 先保存用户提供的原始证据，按指南A—F确定主场景，再选Bad或Good表单。场景、满意度、正式问题/亮点类型与本地Q1—Q7分开。
2. 按表单顺序填写总结、入口、完整会话、任务预期、客观实际结果、分析或完成过程、类型及场景、分级依据、复现和平台等。Good的难点和如何完成不能换成Bad的问题分析。
3. 第一轮到末轮逐轮保留用户原话、小微完整回复和截图；单独记录真实点击、工具页面、附件及提醒状态。缺失前文明确缺失，不把可见轮次当完整轮数。
4. Bad填“复现出问题的次数”，Good填“一次办成的次数”；两者含义不同。截图张数不是测试次数。Bad可核实仅出现一次且未重试时填测试1、问题出现1；Good只测一次时测试次数填1，一次办成按事实填0或1，纠错后才办成不算一次到位。次数本身不明继续待补，不机械填1。
5. 实际结果栏只陈述做了什么；分析栏再写差异、影响、待验证原因及改进。证据不足的D候选不直接选择D。
6. 补齐必填后再考虑提交。确认项默认不勾选，由参赛者实际阅读并确认。原始证据留本地，脱敏后走官方私密渠道。

## 与原指南和旧项目说明不同的地方

以下是**老师提供的本版模板口径**，不宣称已联网验证当前正式计分细则。旧笔记保留来源和日期，以这里作为当前记录方式。

| 项目 | 本版模板明确内容 | 记录时处理 |
| --- | --- | --- |
| 平台Issue标题 | Bad为`Bad Case`、Good为`Good Case`，明文要求不修改 | 不再改成案例ID或中性编号；结论分别放问题总结/亮点总结，公开属性不放隐私 |
| 报告标题 | 默认`测试报告`，未另写禁改标题 | 保留默认，不声称三份都有相同禁改原文 |
| Bad评比范围 | 只取最后30条Bad数据评比 | 不是必须凑30条，也不等于最多只准提交30条 |
| Good评比范围 | 只取最后10条Good数据评比 | 不等于10条都会加分 |
| Good加分 | 确认优质每条2分，最多5条、封顶10分 | 不能凭已提交数量预填成绩 |
| Good等级 | 下拉允许A或B；C/D改用Bad | B档如实说明瑕疵/纠错；是否算优质由评审确认 |
| 无效反馈 | 不参与正向计分，也不倒扣，仅计入分级准确性分母 | 纠正“无效就直接倒扣”的旧概括；仍需严格排除无效反馈 |
| 客户端平台 | iOS、Android、鸿蒙、不确定 | 无PC选项不等于明确禁止PC；PC记录不伪填手机，真实环境留存，正式口径待确认 |
| 问题类型/亮点类型 | Bad24项、Good10项 | 使用原选项，不将Q1—Q7替代正式分类 |
| 报告跨案例规律 | 至少两个已提交案例支撑一个规律 | 待测方案、未提交草稿不冒充已提交案例；不足时如实写证据不足 |

“最后30/10条”没有解释按创建还是更新时间排序、删除/重提如何计入。台账保留实际时间和顺序，窗口状态标“待正式口径核对”，不发明删改策略。

Good允许B但复现选项都围绕“一次办成”。如果只有纠错后完成、一次到位次数为0，应保留真实次数和过程；下拉没有精确选项时标待确认，不虚构一次成功或自行给源表单新增选项。

报告的“满意度分级说明”描述出现“严重问题（P0/P1）”，但没有定义映射。本项目P0/P1/P2仍只表示探索执行顺序；报告说明实际A/B/C/D及边界，不由这一句建立新严重度规则。

## 必填与附件

Bad的“复现步骤与触发条件”必填，只出现一次也要说明；Good的触发条件说明选填。附件虽在YAML中为选填，图片、文件、小工具任务仍应按字段说明附必要原始输入与产物，不能用选填逃掉证据。

报告“隐私与安全分析”必填，没有相关探索时写“未进行相关探索”；深挖代表案例引用真实Bad Issue编号。总结的是实际方法与规律，不把24个待测任务写成已执行成果。
